=== page: hash-table-internals
title: How a hash table works inside
topic: hashing
kind: mechanics
summary: Hash function, bucket array, and why lookup is O(1) on average — the mechanism behind unordered_map.
prereqs: cx-big-o
related: hash-collisions, hash-load-factor-and-rehashing, cpp-unordered-map-set
--- picture | The picture | write
✍️ A hash table is an **array of buckets** plus a **hash function** h(key) that turns any key into a bucket index: `bucket = h(key) % bucketCount`.
✍️ To insert, compute the bucket and put the key there. To look up, compute the same bucket and look only there.
✍️ Because the bucket is computed, not searched for, the cost does not depend on how many keys are stored — as long as each bucket holds only a few keys.

--- hash-function | What a good hash function does | mixed
✍️ Deterministic (same key → same index every time) and spreads keys **evenly** across buckets.
- For integers, `std::hash<int>` in GCC is the identity function; the modulo by a prime bucket count does the spreading.
- For strings, the hash mixes every character, so hashing a string of length L costs O(L). A map with long string keys is O(L) per operation, not O(1).

--- why-o1 | Why "O(1)" is an average | write
✍️ If n keys are spread over about n buckets, each bucket holds about 1 key on average, so a lookup checks ~1 key → O(1) **expected**.
✍️ If many keys land in the same bucket (collisions), that bucket becomes a list and lookup degrades toward O(n). That is the worst case. See [[hash-collisions]].

--- interview | What gets asked | screenshot
- "How does a HashMap work internally?" — array of buckets, hash function, collision handling (chaining), load factor and rehashing.
- "What happens when two keys have the same hash?" — collision; both are stored in the same bucket's list (or probed to the next slot in open addressing).
- "Why is the worst case O(n)?" — all keys could collide into one bucket.
- Java-specific follow-up: since Java 8, a bucket with many entries becomes a balanced tree, making the worst case O(log n). C++ `unordered_map` does not do this.

=== page: hash-collisions
title: Collisions — chaining vs open addressing
topic: hashing
kind: mechanics
summary: Why collisions are unavoidable and the two standard ways of handling them, with their trade-offs.
prereqs: hash-table-internals
related: hash-load-factor-and-rehashing
--- unavoidable | Why collisions are unavoidable | write
✍️ There are far more possible keys than buckets (pigeonhole principle), so some distinct keys must share a bucket. A hash table is designed to handle collisions, not avoid them.

--- chaining | Separate chaining | write
✍️ Each bucket holds a linked list (or small vector) of all keys that hashed there. Insert = append to the bucket's list; lookup = scan that list.
✍️ Cost of an operation = O(1 + length of that bucket's list). With a good hash and load factor ≤ 1, the expected length is O(1).
This is what `std::unordered_map` uses (GCC/libstdc++).

--- open-addressing | Open addressing | mixed
✍️ All keys live in the bucket array itself. On collision, **probe** for the next free slot: linear probing (i+1, i+2, …), quadratic probing, or double hashing.
- Faster in practice (cache-friendly, no pointers) but degrades badly as the table fills, and deletion needs "tombstones".
- Used by Python's `dict` and many high-performance hash maps.

--- compare | Comparison | screenshot
| | Chaining | Open addressing |
|---|---|---|
| storage | bucket array + list nodes | one flat array |
| load factor > 1 | still works | impossible |
| cache behaviour | poorer (pointer chasing) | better |
| deletion | simple | needs tombstones |

=== page: hash-load-factor-and-rehashing
title: Load factor, rehashing and reserve
topic: hashing
kind: mechanics
summary: How the table grows to keep buckets short, why that keeps inserts O(1) amortised, and how reserve avoids the cost.
prereqs: hash-table-internals, cx-amortised-analysis
related: cpp-unordered-map-set
--- load-factor | Load factor | write
✍️ Load factor α = (number of keys) / (number of buckets). It is the average bucket length.
✍️ `unordered_map` keeps α ≤ `max_load_factor()` (default 1.0). When an insert would exceed it, the table **rehashes**.

--- rehash | Rehashing | write
✍️ Rehash = allocate a bigger bucket array (roughly double), and re-insert every key into its new bucket. One rehash costs O(n).
✍️ Because the size doubles, rehashes happen after 1, 2, 4, 8, … inserts. Total rehash work over n inserts < 2n → **O(1) amortised per insert** (same argument as [[cx-amortised-analysis#vector]]).

--- reserve | reserve | mixed
✍️ `mp.reserve(n)` allocates enough buckets for n keys up front, so no rehash happens during the n inserts. Use it when you know the final size; it can make hash-heavy solutions noticeably faster.
- Iterators are invalidated by a rehash: never hold an iterator across inserts.

=== page: hash-frequency-counting
title: Frequency counting
topic: hashing
kind: pattern
summary: Count how many times each value occurs in one pass, then answer questions about counts — anagrams, majority, duplicates, first unique.
prereqs: cpp-unordered-map-set, cpp-container-choice
related: hash-boyer-moore-voting, heap-top-k, sw-frequency-map-window
--- idea | Idea | write
✍️ One pass builds a table `count[value] = number of occurrences`. Every later question about "how many times" becomes an O(1) lookup instead of an O(n) scan.
✍️ Use an array when values are small and dense (letters → `int cnt[26]`), a hash map otherwise.

--- recognise | Recognise it | write
✍️ "anagram", "same characters", "permutation of", "appears more than", "most frequent", "first unique / non-repeating", "duplicate", "can be constructed from".
✍️ The order of elements does not matter, only the multiset of values.

--- think | Brute force → counting | mixed
Brute force for "is t an anagram of s": sort both and compare (O(n log n)), or for each character of s, search and remove it from t (O(n²)).
✍️ Bottleneck: searching for each character individually.
✍️ Fix: two strings are anagrams exactly when every character has the same count in both. Counting is O(n) and needs no search.

--- template | Template | write
```cpp
// two strings same multiset of lowercase letters
bool sameCounts(const string& s, const string& t) {
    if (s.size() != t.size()) return false;
    int cnt[26] = {0};
    for (char c : s) cnt[c - 'a']++;
    for (char c : t) cnt[c - 'a']--;       // cancel out
    for (int k = 0; k < 26; k++) if (cnt[k] != 0) return false;
    return true;
}

// general values
unordered_map<int,int> freq;
for (int x : a) freq[x]++;
for (auto& [val, c] : freq) { /* answer using counts */ }
```
✍️ One table with `++` for the first input and `--` for the second is cleaner than two tables.

--- variations | Variations | screenshot
- Ransom note: every letter of the note must have count ≤ its count in the magazine (LeetCode 383).
- First unique character: count, then scan the string again and return the first index with count 1 (LeetCode 387). Two passes — the second pass restores order.
- Group anagrams: the count array itself (or the sorted string) becomes a **key** ([[hash-derived-keys]]).
- Top k frequent: count, then pick the k largest counts with a heap or buckets ([[heap-top-k]]).
- Counts inside a moving window → [[sw-frequency-map-window]].

--- pitfalls | Pitfalls | write
✍️ Check lengths first for anagram-type problems: different lengths can never match, and the check avoids out-of-range assumptions.
✍️ `freq[x]` on a missing key inserts it ([[cpp-unordered-map-set#bracket-trap]]). Harmless while counting; harmful when you later use `freq.size()` as "number of distinct values".

--- complexity | Complexity | screenshot
O(n) time. Space O(k) for k distinct values — O(1) when the alphabet is fixed (26 letters), O(n) in general.

=== page: hash-complement-lookup
title: Complement lookup — store what you have seen, look up what you need
topic: hashing
kind: pattern
summary: For each element compute the partner it needs, ask a hash map whether that partner has already appeared, then record the element. Turns pair search from O(n²) into O(n).
prereqs: cpp-unordered-map-set, meta-bottleneck-method
related: tp-opposite-ends, ps-prefix-sum-hashmap
--- idea | Idea | write
✍️ Pair problems ask: does some earlier element `y` satisfy a relation with the current `x` (e.g. `x + y = target`)?
✍️ Solve the relation for `y`: `y = target − x`. That `y` is the **complement**. Instead of searching for it, keep every element seen so far in a hash map and ask "is `y` there?" in O(1).
✍️ Reframe: you are not looking for pairs; you are walking once and asking each element "has your partner already walked past?"

--- recognise | Recognise it | write
✍️ "two numbers that add up to / differ by / multiply to …", "pair with …", "exists i < j such that …".
✍️ Input is **not sorted** (if it is sorted and you need O(1) space, use two pointers instead: [[tp-opposite-ends]]).
✍️ Brute force is two nested loops over pairs.

--- think | Brute force → complement lookup | mixed
Brute force: for every i, for every j > i, check `a[i] + a[j] == target`. O(n²).
✍️ Bottleneck: the inner loop. Its job: "for this `a[i]`, search the rest of the array for the value `target − a[i]`".
✍️ Waste: it searches for one specific, known value. A known value can be looked up in O(1) if it has been stored in a hash map.
Better (two-pass): put every value → index in a map, then for each i look up `target − a[i]` (but make sure it is not i itself).
✍️ Optimal (one-pass): look up first, insert after. Only earlier elements are in the map, so an element can never pair with itself, and the first pair found is returned immediately.

--- self-pairing | The order rule: check before insert | write
✍️ Always **query before inserting** the current element.
✍️ If you insert first, `x` can match itself when `target = 2x` (e.g. `[3, 2, 4]`, target 6 would wrongly return [0, 0]).
✍️ Querying first also handles genuine duplicates correctly: `[3, 3]`, target 6 → at i = 1, the map already holds the first 3 → returns [0, 1].

--- template | Template | write
```cpp
vector<int> twoSum(vector<int>& a, int target) {
    unordered_map<int,int> seen;              // value -> index
    for (int i = 0; i < (int)a.size(); i++) {
        int need = target - a[i];
        auto it = seen.find(need);
        if (it != seen.end()) return {it->second, i};
        seen[a[i]] = i;                       // insert AFTER the check
    }
    return {};
}
```

--- variations | Variations | screenshot
- Count pairs instead of finding one: map stores value → **count**; add `count[need]` to the answer at each step (LeetCode 1512 counts equal pairs: need = x itself).
- "Two equal values within distance k": map stores value → **last index**; check `i − last[x] ≤ k` (LeetCode 219).
- Contains duplicate: complement is the value itself → a set is enough (LeetCode 217).
- Subarray sums: the "element" is a prefix sum and the complement is `prefix − k` ([[ps-prefix-sum-hashmap]]).
- Sorted input → two pointers, O(1) space ([[tp-opposite-ends]]).

--- pitfalls | Pitfalls | write
✍️ Inserting before checking → self-pairing bug (see above).
✍️ Storing index when you need count (or vice versa). Decide what the map value is from what the question asks: indices → index; number of pairs → count.
✍️ `target − a[i]` can overflow in variants with large values; use `long long`.

--- complexity | Complexity | screenshot
O(n) time average (one lookup and one insert per element). O(n) space for the map. The trade: brute force is O(n²) time and O(1) space.

--- interview | Interview follow-ups | screenshot
- "The array is sorted — can you use O(1) space?" → two pointers from both ends.
- "Return all unique pairs" → sort + two pointers with duplicate skipping ([[tp-skip-duplicates]]).
- "What if the data is a stream you cannot store?" → in general impossible; with a bounded value range use a fixed-size presence array.

=== page: hash-derived-keys
title: Grouping by a derived key
topic: hashing
kind: pattern
summary: Compute a canonical key for each item so that items that "belong together" share a key, then group them in a map from key to list.
prereqs: hash-frequency-counting, cpp-unordered-map-set
related: hash-frequency-counting
--- idea | Idea | write
✍️ Two items belong to the same group exactly when some **canonical form** of them is equal. Compute that form, use it as a map key, and push each item into `groups[key]`.
✍️ Group anagrams: canonical form = the sorted string, or the 26-count signature.

--- recognise | Recognise it | write
✍️ "group", "bucket", "classify", "all items that are equivalent under …", "isomorphic", "same pattern".

--- template | Template | write
```cpp
unordered_map<string, vector<string>> groups;
for (const string& w : words) {
    string key = w;
    sort(key.begin(), key.end());          // canonical form
    groups[key].push_back(w);
}
vector<vector<string>> out;
for (auto& [k, g] : groups) out.push_back(move(g));
```

--- key-choice | Choosing the key | mixed
✍️ Sorted string: simple, O(L log L) per word.
✍️ Count signature (e.g. "1#0#2#…" for 26 counts): O(L + 26) per word, better for long words.
- Pattern keys for "word pattern / isomorphic strings": map each character to the index of its first appearance, e.g. "egg" → [0,1,1], "add" → [0,1,1].

--- complexity | Complexity | screenshot
O(n · cost of computing one key). With sorted keys: O(n · L log L). Space O(n · L) to store the groups.

=== page: hash-set-runs
title: Hash set membership and the start-of-run trick
topic: hashing
kind: pattern
summary: Put all values in a set so membership is O(1), then only start counting a run from values whose predecessor is missing — finding the longest consecutive run in O(n).
prereqs: cpp-unordered-map-set
related: hash-frequency-counting
--- idea | Idea | write
✍️ A run of consecutive integers `v, v+1, v+2, …` has exactly one **start**: the value `v` such that `v − 1` is not present.
✍️ Put every value in an `unordered_set`. For each value that is a start, walk upward (`v+1`, `v+2`, …) while present and measure the length.
✍️ Each value is visited by at most one upward walk (the walk of its own run's start), so the total work is O(n) even though there is a loop inside a loop.

--- recognise | Recognise it | write
✍️ "longest consecutive", "sequence of consecutive integers", "in O(n)" with unsorted input — sorting would give O(n log n), so the O(n) requirement is the hint to use a set.

--- think | Brute force → start-of-run | mixed
Brute force: for every value, walk upward checking membership with a linear scan. O(n) per check → O(n³) worst, or O(n²) with a set.
Better: sort, then scan counting runs (skip duplicates). O(n log n).
✍️ Bottleneck of the set version without the trick: a run of length L is re-walked from each of its L elements → O(n²) on input like 1..n.
✍️ Fix: only walk from starts. A value with a predecessor is never a start, so it is never the beginning of a walk.

--- template | Template | write
```cpp
int longestConsecutive(vector<int>& a) {
    unordered_set<int> s(a.begin(), a.end());
    int best = 0;
    for (int v : s) {                       // iterate the SET, not the array (duplicates!)
        if (s.count(v - 1)) continue;       // not a start
        int len = 1;
        while (s.count(v + len)) len++;
        best = max(best, len);
    }
    return best;
}
```

--- pitfalls | Pitfalls | write
✍️ Iterate over the **set**, not the original array. With many duplicates of a start value, iterating the array would re-walk the same run once per duplicate → O(n²).
✍️ Empty input → 0. Handled naturally if `best` starts at 0.
- `v + len` could overflow at INT_MAX; LeetCode's range (±10⁹) keeps it safe.

--- complexity | Complexity | screenshot
O(n) average time: n inserts, and each value is touched once by the "is it a start" check and at most once by a walk. O(n) space.

=== page: hash-boyer-moore-voting
title: Boyer–Moore voting — the majority element in O(1) space
topic: hashing
kind: pattern
summary: Pair off different values against each other; the value that appears more than n/2 times always survives. One pass, two variables.
prereqs: hash-frequency-counting
related: hash-frequency-counting
--- idea | Idea | write
✍️ Keep a `candidate` and a `count`. For each x: if count is 0, adopt x as the candidate. If x equals the candidate, count++; otherwise count--.
✍️ Each "count--" cancels one copy of the candidate against one different value. A value occurring more than n/2 times cannot be fully cancelled, because there are fewer than n/2 other values to cancel it with.

--- recognise | Recognise it | write
✍️ "majority element", "appears more than ⌊n/2⌋ times", **plus** "O(1) space" or "can you do it without extra memory?".
✍️ A ban on extra space is itself the hint: frequency maps are out, so a counting/cancelling argument is in.

--- think | Brute force → voting | mixed
Brute force: for each value count its occurrences with a scan. O(n²).
Better: frequency map, return the value with count > n/2. O(n) time, O(n) space.
Also valid: sort, return the middle element `a[n/2]` (the majority must cover the middle). O(n log n), O(1).
✍️ To reach O(n) time *and* O(1) space you need to avoid storing counts for every value. Observation: you only care about **one** value, the one that survives cancellation.

--- why-it-works | Why it works (proof sketch) | mixed
✍️ Think of each count-- as removing a pair of two different elements from the array. Removing a pair of different elements never changes which element is the majority of what is left (the majority loses at most one copy per pair, and so does the rest).
✍️ At the end, what remains is all copies of one value — the candidate. If a majority exists, it must be that value.
- If a majority is **not guaranteed**, do a second pass to count the candidate and verify count > n/2.

--- template | Template | write
```cpp
int majorityElement(vector<int>& a) {
    int cand = 0, cnt = 0;
    for (int x : a) {
        if (cnt == 0) cand = x;     // adopt BEFORE comparing
        cnt += (x == cand) ? 1 : -1;
    }
    return cand;                    // guaranteed majority; otherwise verify with a 2nd pass
}
```

--- variations | Variations | screenshot
- More than n/3 times (LeetCode 229): at most two such values exist. Keep **two** candidates and two counts; a value different from both decrements both. Always verify with a second pass.
- General: more than n/k times → at most k−1 candidates (Misra–Gries).

--- pitfalls | Pitfalls | write
✍️ Order inside the loop: check `cnt == 0` and adopt the new candidate **before** the comparison, otherwise the first element of a new block is counted against the old candidate.
✍️ The final candidate is only guaranteed correct when a majority exists. Without the guarantee, verify.

--- complexity | Complexity | screenshot
O(n) time, O(1) space. Verification pass (if needed) is another O(n).
